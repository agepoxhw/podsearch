Take-home exercise: search podcast audio by meaning

Build a small system that lets a user type a text query and find the moments in podcast audio where the speakers talk about that topic. The output is a ranked list of chunks.

The system runs on a local Kubernetes cluster and indexes audio with a speech embedding model. It never produces a transcript.

Every component runs inside one local Kubernetes cluster.

Time and tools

Plan for about one working day. Use any AI coding tools you like; we use Claude Code every day and expect you to. In the interview, we walk through your architecture together, so make sure you understand what you submit.

Many parts of this exercise are probably new to you. That is intentional: we want to see how you learn an unfamiliar area and get it working.

Requirements

  1. Cluster. Run everything on a local Kubernetes cluster of your choice, such as kind, k3d, k3s or minikube. A single command brings the whole system up from a clean checkout.
  2. Object store. Run an S3-compatible object store of your choice inside the cluster. You load audio by uploading files to it.
  3. Ingestion. An in-cluster process picks up newly uploaded audio, splits it into 10-second chunks, embeds each chunk, and writes the vectors to the vector database. Assume new audio keeps arriving: the system indexes it without a manual step or a restart.
  4. Model. Embed audio chunks with Meta SONAR's English speech encoder (sonar_speech_encoder_eng) and embed queries with its text encoder (text_sonar_basic_encoder). Both map into the same vector space. See Meta SONAR on GitHub.
  5. Vector database. Store chunk vectors in a vector database of your choice, running in the cluster.
  6. Search API. An HTTP endpoint takes a text query and returns ranked hits — decide what a hit should contain. Return only hits whose confidence, the cosine similarity between the query vector and the chunk vector, is at least 0.20.

Recommendations

  • Orchestration. Use Ray Data to orchestrate the ingestion pipeline — chunking, embedding, and writing vectors.
  • UI. Not a requirement, but build a simple page with a search box and a player for each hit — it is the fastest way to check your own results before you write them up. Styling does not matter.

What to submit

Send a link to a Git repository that contains:

  1. The code and the cluster manifests or charts.
  2. A README.md with:
    • the bring-up command and any prerequisites;
    • a short architecture description;
    • your main design choices and the alternatives you rejected;
    • what you learned and what was hardest;
    • what you would change to index 1,000 times more audio.
  3. Results for these queries: Putin, Ukraine, Middle East and Iran. For each one, list the hits you consider correct and any you consider wrong.

What we look for

  • The system comes up from a clean checkout and returns sensible results.
  • Your design choices are deliberate, and you can explain the trade-offs.
  • You understand the code you submitted, including the parts an AI tool wrote.
  • You can say where the approach works well and where it breaks.
